# Releasing

The version lives in `version` in `cli/Cargo.toml`. The npm packages and the Homebrew formula take it from the release. The skill stub `skills/agent-terminal/SKILL.md` repeats it in `metadata.version`, because `npx skills add` and the Claude Code plugin marketplace copy that file as it is in the repository; `cargo test` fails while the two differ.

## Cut a release

An agent cuts a release end to end with these steps. Keep npm and Homebrew state from the checks inside the checkout (`npm_config_userconfig`, `npm_config_cache`, a scratch `--prefix`).

1. **Collect the commits since the last tag.** `git fetch --tags origin`, then `git log --no-merges --format='%h %s%n%b' "$(git describe --tags --abbrev=0 origin/main)..origin/main"`. Before the first release there is no tag: take every commit on `origin/main`.
2. **Write the changelog section.** In `CHANGELOG.md`, turn the commits and any entries under `## Unreleased` into a new `## <version> (<YYYY-MM-DD>)` section, placed below an empty `## Unreleased`. Group the entries under `### Features` (`feat`), `### Fixes` (`fix`), `### Performance` (`perf`) and `### Other changes` (any other commit a user would notice, such as a new platform or install channel). Leave out `chore`, `ci`, `test` and `style` commits and anything a user can't see, and drop empty groups. Write one line per change, in the user's words, with commands and flags in backticks; a breaking change (`!` or `BREAKING CHANGE:`) comes first in its group and starts with `**Breaking:**`.
3. **Bump the version.** Set `version` in `cli/Cargo.toml` and `metadata.version` in `skills/agent-terminal/SKILL.md` to the new version, and run `cargo build` in `cli/` so `Cargo.lock` follows. Then run the release's preflight from the repository root, `node npm/preflight.js --tag v<version>`, and go on only when it ends with `v<version> can be released`.
4. **Commit.** `git commit -m "chore: release v<version>" -- CHANGELOG.md cli/Cargo.toml cli/Cargo.lock skills/agent-terminal/SKILL.md` on a branch, push it and open a pull request to `main`.
5. **Wait for CI.** `gh pr checks <pr> --watch` until every check passes, `dist plan` included, then merge the pull request.
6. **Tag and push.** `git fetch origin main`, check that `git log -1 origin/main` is the release commit, then `git tag v<version> origin/main` and `git push origin v<version>`.
7. **Watch the run.** `gh run list --workflow release.yml --branch v<version>` names the run and `gh run watch <run> --exit-status` follows it.
   - A failure before `host` (preflight, builds, npm packages, glibc floor, install test) has released and attested nothing. Fix the cause on `main` through steps 4 and 5, delete the tag (`git push origin :refs/tags/v<version>`, then `git tag -d v<version>`) and tag the fixed commit.
   - A publish job that fails after `host` created the GitHub release: fix its cause and rerun the failed jobs (`gh run rerun <run> --failed`). Publishing skips versions already on npm, and the tag stays where it is.
8. **Verify each channel.**
   - GitHub: `gh release view v<version>` shows the changelog section as the notes, the six archives, a `.sha256` per archive and `sha256.sum`. Download one archive (`gh release download v<version> -p 'agent-terminal-aarch64-apple-darwin.tar.xz'`) and check `gh attestation verify agent-terminal-aarch64-apple-darwin.tar.xz --repo repost-sh/agent-terminal`.
   - npm: `npm view @repost/agent-terminal dist-tags.latest` prints the version, and `npm view @repost/agent-terminal-<platform>@<version> version` does for each platform package. `npm i -g --prefix <scratch> @repost/agent-terminal@<version>`, then `<scratch>/bin/agent-terminal --version`. In a scratch project, `npm i @repost/agent-terminal@<version>` then `npm audit signatures` reports verified attestations.
   - Homebrew: `brew update`, `brew install repost-sh/tap/agent-terminal` (`brew upgrade` when installed), then `agent-terminal --version`.

A tag with a prerelease suffix (`v0.2.0-rc.1`, from `version = "0.2.0-rc.1"`) runs the whole pipeline, preflight included, and creates a GitHub prerelease, but publishes nothing to npm or Homebrew. Use one to rehearse. The preflight wants its own `## 0.2.0-rc.1 (<date>)` section or the `## 0.2.0 (<date>)` section of the release it rehearses, so write the release's section before the first rc. It dry-runs the npm packages under the `next` dist-tag because npm refuses to make a prerelease `latest`.

## What the tag runs

`.github/workflows/release.yml`, generated by [dist](https://axodotdev.github.io/cargo-dist/) from `dist-workspace.toml`:

The preflight (`preflight.yml`, job `custom-preflight`, `local-artifacts-jobs` in `dist-workspace.toml`) runs `node npm/preflight.js --tag <tag>` next to the builds, on prerelease tags too. It fails when the tag isn't `v` + the version in `cli/Cargo.toml`, when `CHANGELOG.md` has no section for that version, or when `npm publish --dry-run` refuses any of the seven packages (built from the template without their binaries, which don't exist yet). Everything after the builds waits for it, so the attestations, the GitHub Release and both publish jobs never start after a failed preflight.

1. Builds `agent-terminal` archives for macOS (arm64, x64) and Linux (arm64, x64, glibc and musl) with the Rust toolchain `rust-toolchain.toml` pins. Each Linux archive builds in a container image for its target and architecture (`github-custom-runners` in `dist-workspace.toml`, see "glibc floor, build images and toolchain pins" below): the glibc (gnu) archives in a `manylinux_2_28` image, so they run on glibc 2.28, and the musl archives in a `rust-musl-cross` image. Both images have a C++ compiler, because the binary compiles OpenH264, a C++ library, from source.
2. `npm-packages.yml` checks that each gnu binary needs at most glibc 2.28 (`scripts/glibc-floor.sh`), then packs one npm package per platform (`@repost/agent-terminal-<os>-<cpu>[-musl]`, holding only that binary) and the main `@repost/agent-terminal` package (the launcher in `npm/agent-terminal`, with the platform packages as exact-version optional dependencies). Every package is public (`publishConfig.access`) and names this repository (`repository`), which npm provenance needs; the scope is explained in `docs/adr/0003-npm-package-is-repost-scoped.md`. It then builds the Homebrew formula from the same archives and runs the clean-machine install test (below). Any failure stops the release: the glibc floor check is a job of its own in this workflow (`glibc-floor`), not a step of a build, and `release.yml` runs the workflow as the job `custom-npm-packages`, which `host` (the attestations and the GitHub Release) and both publish jobs wait for, so a binary over the floor publishes nothing.
3. Creates the GitHub Release with the archives, a `.sha256` file per archive and `sha256.sum`. Its title and notes are the version's `CHANGELOG.md` section. Just before it creates the release, `host` attests every release file with GitHub artifact attestations (`github-attestations`, with `github-attestations-phase = "host"`, in `dist-workspace.toml`), so `gh attestation verify <archive> --repo repost-sh/agent-terminal` traces a download to the run that built it, and a tag the preflight or the glibc floor check refuses gets no attestation. dist's default phase would attest in each build job, before either check has passed.
4. Publishes the formula to `repost-sh/homebrew-tap` (`brew install repost-sh/tap/agent-terminal`) and the npm packages (`publish-npm.yml`, through npm trusted publishing with `--provenance` and no token, platform packages first, versions already on npm skipped so a rerun is safe).

## Roll back

npm never lets a version number be used twice, even after unpublishing, so a bad release is contained and replaced, not undone. The npm commands need a maintainer of the `@repost` packages logged in (`npm login`); trusted publishing covers only the workflow's `npm publish`.

1. **Move npm `latest` back** to the last good version: `npm dist-tag add @repost/agent-terminal@<good> latest`. The platform packages follow, because the main package pins them exactly.
2. **Deprecate the bad version**, for the main package and each platform package: `npm deprecate @repost/agent-terminal@<bad> "<what is wrong>; use <good> or later"`, then the same for each `@repost/agent-terminal-<platform>@<bad>`.
3. **Ship a fixed patch version** through the procedure above.
4. **Update the tap formula.** The fixed release pushes its own formula to `repost-sh/homebrew-tap`. Reverting `Formula/agent-terminal.rb` there stops new installs of the bad version but doesn't move existing installs, since `brew upgrade` acts only on a higher version: only the fixed, higher version reaches them.
5. **Never move a tag** of a release that reached `host`: Homebrew and source builds rely on it. To stop the GitHub release showing as the latest, mark it a prerelease (`gh release edit v<bad> --prerelease`).

## Clean-machine install test

The `clean-install` job in `npm-packages.yml` installs the release's own artifacts on fresh runners: Ubuntu x64 and arm64 (glibc), Alpine x64 and arm64 (musl, a `node:24-alpine` container), macOS arm64 (`macos-14`) and macOS x64 (`macos-15-intel`). Each row installs with each channel: npm, pnpm and bun from a local registry holding the packed tarballs (`npm/install-test/registry.js`), the direct release archive after checking it against its `.sha256` (without its trailing blank line, which busybox `sha256sum -c` on Alpine counts as a mismatched entry), and the formula dist generated with its archive URLs pointed at the local archive. Alpine has no Homebrew row, because Homebrew does not run on musl. After installing (`npm/install-test/install.sh`), `npm/install-test/check.sh` asserts, with no TTY, that `--version` and `--json version` print the release's version, that the skill stub `install --skills` writes carries it, and that `open`, `snapshot` and `close` on the line-printer fixture work and `daemon stop` leaves no daemon running; `npm/install-test/offline.sh` then runs the same checks with networking cut (`sandbox-exec` on macOS, a network namespace on Linux).

The `glibc` job runs the gnu binaries on older distributions: Debian 11 (`debian:11`, glibc 2.31), Ubuntu 20.04 (`ubuntu:20.04`, glibc 2.31) and Rocky Linux 8 (`rockylinux/rockylinux:8`, glibc 2.28), each on x64 and arm64. It unpacks the release archive on the runner after checking its `.sha256` (`install.sh archive`), then runs `check.sh` inside a fresh container of that distribution: `--version`, `--json version`, the skill stub, the `open` → `snapshot` → `close` round trip and `daemon stop`, with no TTY. These images have no Node, so the npm channels and the run with networking cut stay on the Ubuntu rows.

It runs before any tag: `.github/workflows/clean-install.yml` builds the six archives the way `release.yml` does, from the same `dist plan`, and runs the same test on them. It runs on every pull request, and on demand from the Actions tab or with:

```sh
gh workflow run clean-install.yml --ref <branch>
gh run watch "$(gh run list --workflow clean-install.yml --branch <branch> --limit 1 --json databaseId --jq '.[0].databaseId')"
```

GitHub offers `workflow_dispatch` only for workflows on the default branch, so until `clean-install.yml` is on `main`, open a pull request (a draft is enough) to run it.

## Change the pipeline

Edit `dist-workspace.toml`, then run `dist generate` with dist 0.33.0 to rewrite `release.yml`. `release.yml` runs `dist plan` on every pull request, and that fails while the generated file is out of date, so a hand edit to `release.yml` cannot land.

A new platform needs a target in `dist-workspace.toml`, a row in `PLATFORMS` in `npm/agent-terminal/lib/platform.js`, and a row in the `clean-install` matrix in `npm-packages.yml` whose `target` and `package` name that platform; `npm/test/platform.test.js` fails until the three agree.

Every release archive (dist's `include`) and every npm platform package (`build-packages.js`) ships `licenses/` next to the binary. A new third-party work built into the binary (a font, a C library) needs its licence text in `licenses/` and a row in `licenses/README.md`.

## glibc floor, build images and toolchain pins

Everything that builds a release is pinned, so an upstream release cannot change or break a release run.

- **glibc floor: 2.28.** The gnu archives run on Linux with glibc 2.28 or later; the `glibc` job above runs them on Debian 11, Ubuntu 20.04 and Rocky Linux 8. The floor comes from the build image: a binary can only require the glibc versions of the glibc it was linked against. `scripts/glibc-floor.sh` checks the result: it reads each binary's version references (`objdump -p`), prints the newest `GLIBC_` version each one requires, and fails when one is above `FLOOR`. The `glibc-floor` job in `npm-packages.yml` runs it on both gnu archives of every release and every clean-install run, before anything is published.
- **Build images**, pinned by digest in `github-custom-runners` in `dist-workspace.toml`. The gnu targets build in `quay.io/pypa/manylinux_2_28_x86_64` and `quay.io/pypa/manylinux_2_28_aarch64`: AlmaLinux 8 with glibc 2.28 and GCC 14 (`gcc-toolset-14`) for OpenH264's C++. They carry no Rust: the build job installs rustup, which installs the pinned toolchain. The musl targets build in `ghcr.io/rust-cross/rust-musl-cross` (`:x86_64-musl`, `:aarch64-musl`), which have a musl GCC with C++ (Ubuntu's `musl-tools` has no musl C++ compiler); their own Rust is replaced by the pinned toolchain too.
- **Rust: 1.98.1**, in `rust-toolchain.toml` at the repository root. rustup reads it wherever cargo runs in this repository, so release builds, the clean-install workflow, CI and local builds all use the same Rust. The pin follows the previous stable release at its latest patch, not the newest stable: when it was set, 1.99.0 was two weeks old and 1.98.1 was the patched 1.98. A brand-new release is where regressions surface (agent-browser's release broke four days after Rust 1.98.0 came out), so move the pin to a release once its first weeks are behind it.
- **dist: 0.33.0**, `cargo-dist-version` in `dist-workspace.toml`. Every workflow installs it from its GitHub release (`cargo-dist-installer.sh`), because crates.io stops at 0.32.0.

To move a pin, change it on a branch and open a pull request: the clean-install workflow builds all six archives with the new pin and runs every install row, the `glibc-floor` job and the `glibc` job on them.

- Rust: set `channel` in `rust-toolchain.toml` and run the checks in `CONTRIBUTING.md` (rustup installs the new toolchain on first use); fix what new lints report in the same pull request.
- dist: set `cargo-dist-version`, install that dist from its GitHub release, run `dist generate` and `dist plan`, and commit the regenerated `release.yml`.
- An image: take the tag's current digest and put tag and digest in `dist-workspace.toml`. For manylinux take the newest dated tag (`YYYY.MM.DD-N`) listed at `https://quay.io/repository/pypa/manylinux_2_28_x86_64?tab=tags` and `.../manylinux_2_28_aarch64?tab=tags`; for rust-musl-cross the `x86_64-musl` and `aarch64-musl` tags. `docker buildx imagetools inspect <image>:<tag>` prints the digest.
- The floor: build the gnu targets in images with the new glibc (`manylinux_2_<minor>`), set `FLOOR` in `scripts/glibc-floor.sh`, and change the `glibc` job's distributions in `npm-packages.yml` to the oldest ones the new floor supports.

## Check locally

```sh
node --test 'npm/test/*.test.js'
dist plan
node npm/preflight.js --tag v<version>
```

To check gnu binaries against the glibc floor (it needs `objdump`, from binutils on Linux and from the Xcode command line tools on macOS), for example the ones in a clean-install run's `artifacts-build-local-*-linux-gnu` artifacts:

```sh
sh scripts/glibc-floor.sh agent-terminal-x86_64-unknown-linux-gnu/agent-terminal agent-terminal-aarch64-unknown-linux-gnu/agent-terminal
```

To build a musl archive the way the release does, run dist in that target's image from `dist-workspace.toml` (arm64 shown; the archive lands in `target/distrib`, the Linux build in `target/musl`):

```sh
docker run --rm -v "$PWD:/src" -w /src -e CARGO_TARGET_DIR=/src/target/musl \
  ghcr.io/rust-cross/rust-musl-cross:aarch64-musl@sha256:<digest in dist-workspace.toml> \
  sh -c "curl --proto '=https' --tlsv1.2 -LsSf https://github.com/axodotdev/cargo-dist/releases/download/v0.33.0/cargo-dist-installer.sh | sh \
    && dist build --artifacts=local --target=aarch64-unknown-linux-musl"
```

To run the install test for one channel on this machine, build the release archives (`dist build`) and the formula (`dist build --artifacts=global`), turn the archives into npm tarballs (`node npm/build-packages.js --manifest <plan.json> --artifacts target/distrib --out target/npm`, then `npm pack` each directory in `target/npm/@repost`), build `line-printer`, and put the tarballs in `<artifacts>/npm`, this machine's archive and its `.sha256` in `<artifacts>/archive` and `agent-terminal.rb` in `<artifacts>/formula`. The homebrew channel installs into your Homebrew, so run it on a runner or a machine you can spare. Then, with a short `<state>` folder (the daemon's socket path lives in it):

```sh
sh npm/install-test/install.sh npm <artifacts> <state> @repost/agent-terminal-darwin-arm64
sh npm/install-test/check.sh <state> <version> <line-printer>
sh npm/install-test/offline.sh sh npm/install-test/check.sh <state> <version> <line-printer>
```

## One-time setup

The owner runs `scripts/one-time-setup.sh` once, from the repository root, with `gh` logged in as an owner of `repost-sh`. It opens each page, says what to fill in, sets the secret with `gh`, and remembers its progress in `.superpowers/one-time-setup/` (gitignored), so a re-run skips what is done. `scripts/one-time-setup.sh --check` only reads: it lists what is left and exits 0 when nothing is.

- The `repost-sh/homebrew-tap` repository, public, with a README so it has a branch to push to, and a `HOMEBREW_TAP_TOKEN` secret on `repost-sh/agent-terminal`: a fine-grained token owned by `repost-sh` with Contents read and write on `repost-sh/homebrew-tap` only. When it expires the Homebrew publish fails; delete the secret and run the script again.
- A trusted publisher on npmjs.com for each of the seven packages, `@repost/agent-terminal` and the six `@repost/agent-terminal-<platform>` (package settings, Trusted Publisher): publisher GitHub Actions, organization or user `repost-sh`, repository `agent-terminal`, workflow filename `release.yml`, no environment. npm checks the workflow the tag triggered, `release.yml`, whose `custom-publish-npm` job calls `publish-npm.yml` (job `publish`, which runs `npm publish`); naming `publish-npm.yml` fails. No npm token is stored in the repository.
- **A trusted publisher needs a package that already exists.** npm's `npm trust` reference lists as a prerequisite "The package you're configuring must already exist on the npm registry" (https://docs.npmjs.com/cli/v12/commands/npm-trust/), and the website's Trusted Publisher section is in the settings of an existing package (https://docs.npmjs.com/trusted-publishers). So for each package not yet on npm the script runs a one-time bootstrap: the owner creates a granular token (read and write on the `@repost` scope, bypassing two-factor authentication, expiring the next day), the script publishes a placeholder `0.0.0-bootstrap` under the dist-tag `bootstrap` with it, the owner deletes the token, and the trusted publishers are added right after. The token lives only in the script's process, never in a file or a secret. npm never frees a version number, so `0.0.0-bootstrap` stays listed; the first release publishes `0.1.0` as `latest`.
- **A new trusted publisher expires after 2 days** unless a publish uses it (https://docs.npmjs.com/trusted-publishers), so run the script once `v0.1.0-rc.1` has passed and tag `v0.1.0` within two days. Run later, `--check` reports the expired ones and the script walks through deleting and adding them again.
